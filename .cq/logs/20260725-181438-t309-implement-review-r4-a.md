# T309 implementation review R4 A

Verdict: **disapprove**

Reviewed commit: `6994ecb95c5ffb1143c46db4b18b3d688fb7b779`

## Stable evidence

- The ownership-transfer API and one-group staging tests pass under ordinary and race execution.
- Writer-error terminality applies to the decided group, not the owner lifetime. A later `Send` must remain possible under the compatibility contract.
- No current production caller reaches the adaptive-controller test seam, but the seam retains an unsafe lock ordering.

## Blocking finding

T309 requires one synchronous batch request per original `Send`, with the owner assigning outer/group/index state while iterating the request. The implementation instead:

- defines a one-frame request at `internal/bind/fec_sender.go:81-90`;
- allocates `len(bufs)` requests and two channels per frame at `internal/bind/multipath.go:3192-3203`;
- assigns all outer sequence numbers in the caller at `internal/bind/multipath.go:3195`; and
- submits/admission-waits one frame at a time at `internal/bind/multipath.go:3205-3210`.

The 257-buffer test proves progress but does not prove the required request ownership/cursor design or bounded request/channel allocation.

## Additional defect

The stop protocol can enqueue or admit work after `Stop` closes the stop channel because the selects at `internal/bind/fec_sender.go:170-181` and `:272-294` choose nondeterministically among ready cases. Lifecycle unpublishing currently prevents demonstrated late wire exposure, but the behavior violates the explicit stop contract and permits retained-buffer/work races.

## Question resolved for the revision

`driveAdaptiveControllerLocked` requires `m.mu` while synchronously waiting on the owner. The owner can simultaneously require `m.mu` in decision/adaptive work, creating a dormant lock cycle in tests or future callers. Remove or redesign the seam so synchronous owner submission never occurs while `m.mu` remains held.
